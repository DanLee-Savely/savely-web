## 1. 목적과 범위

### 1-1. 메우는 한계
직접 입력은 세이블리의 핵심이지만, 폼을 열고 금액 · 날짜 · 카테고리 · 결제수단을 하나씩 고르는 일은 매일 하기 어렵다. 기록이 끊기면 돌아보기도 없다.
**한 문장으로 적으면 기록 초안을 만들어 주고, 사용자는 확인하고 저장만 하면 되게** 해서 입력 마찰을 줄인다.

### 1-2. 원칙 (바꾸지 않는다)
1. **앱이 정본이다.** 동작 · 문구 · 검증 한도는 모바일 앱의 대화형 기록을 그대로 따른다. 웹에서 다르게 하는 것은 §3에만 적는다.
2. **AI는 사실만 정리한다.** OpenAI 출력 형식에 이유 · 기분 · 메모 칸이 아예 없다(구조로 막음).
3. **확인 후 저장.** 초안은 카드일 뿐이다. 저장 확인 창에서 사용자가 눌러야 저장된다.
4. **같은 검증.** 규칙이 만든 초안이든 OpenAI가 만든 초안이든 같은 검증기를 거치고, 저장할 때 서버가 기존 도메인 클래스로 다시 검사한다.
5. **OpenAI는 보조다.** 규칙이 읽은 부분은 보내지 않는다. OpenAI가 실패하거나 한도에 걸려도 규칙이 만든 초안은 그대로 쓴다.

### 1-3. 이번에 만드는 것
- 모든 `/app` 화면 오른쪽 아래 **「대화로 기록하기」 버튼** → 오른쪽 **대화 패널**
- 규칙 기반 파서(앱에서 이식) + 읽지 못한 부분의 OpenAI 정리
- 초안 카드 · 수정 시트 · 저장 확인 · 저장 요약 · 나가기 확인 · 직접 입력 전환
- 추가 기능: A 자주 적는 항목 · B 금액만 먼저 적고 나중에 채우기 · C 고정지출 · 고정수입 등록 · E 대화로 카드 등록 · F 「할 수 있는 일」 안내 · G 문장의 날짜 읽기
- 기록 종류 상환 · 저축 추가와 카테고리 41종(기록 체험판 화면 · DB 포함, §4 · §5)
- 요청 제한 · 하루 상한 · 전송 고지 · 처리방침 갱신
- 문서: 이 명세 · QA · README

### 1-4. 이번에 만들지 않는 것
| 기능 | 이유 |
|---|---|
| 음성 입력 | 텍스트만(사용자 2026-11-24) |
| 영수증 · 사진 인식 | 영수증에는 카드번호 일부 같은 개인정보가 많다 |
| 대화 내역 저장 · 다시 보기 | 원문을 저장하지 않는다(§8) |
| AI가 이유 · 기분 추정 | 원칙 2 |
| 대화로 기존 기록 고치기 · 지우기 | 앱과 같다. 수정은 카드 · 기록 화면에서 |
| D 홈 화면 위젯 | 웹에는 홈 화면 위젯이 없다 |
| 정산 연결 | 웹 체험판에는 정산이 없다 |
| 고정지출 · 카드 명령을 OpenAI로 읽기 | 앱도 규칙으로만 읽는다 |

## 2. 문장이 초안이 되기까지

```
문장(500자 이내) ── 보내기
  ▼ (서버 · Server Action)
① 도움말인가? ─ 예 → 「할 수 있는 일」 목록 (F)
② 고정지출 명령인가? ─ 예 → 등록 카드 · 삭제 확인 · 목록 (C)
③ 카드 등록인가? ─ 예 → 카드 등록 카드 (E)
④ 기록 규칙 파서 → 초안 + 읽지 못한 조각
  ▼ 읽지 못한 조각이 있고, OpenAI를 쓸 수 있으면(요청 제한 · 하루 상한 · 잔액)
⑤ OpenAI에 그 조각만 보낸다 → 초안 추가
  ▼
⑥ 검증기 → 통과한 것만 초안 카드. 끝까지 못 읽은 조각은 「이 부분은 알아듣지 못했어요: …」(앱 문구)
```
- 읽는 순서 ①~④는 앱과 같다.
- OpenAI가 실패 · 시간 초과 · 요청 제한 · 하루 상한 · 잔액 소진이면 ⑤를 건너뛴다. 사용자에게 보이는 결과는 앱(규칙만)과 같다.

### 2-1. OpenAI에 보내는 경우
- **확정:** 규칙 파서가 읽지 못한 조각.
- **확정(U-W1, 2026-11-25):** 내용은 있는데 카테고리를 찾지 못한 초안의 카테고리 추천. 금액만 적은 초안(「4500」)은 보내지 않는다 — B(나중에 채우기)와 겹치지 않게.

### 2-2. OpenAI가 만든 카드 표시 (확정 · U-W2, 2026-11-25)
OpenAI가 만들거나 카테고리를 채운 카드에 작은 표시 「AI가 정리」를 붙인다. 무엇을 AI가 했는지 사용자가 알 수 있게 하고, 검증할 때도 확인하기 쉽다.

### 3-1. 추가 기능의 웹 구현 (2026-11-26)

| 기능 | 웹 동작 | 브라우저 저장소 |
|---|---|---|
| A 자주 적는 항목 | 공용 기록에서 이번 달과 앞 두 달 · 구분 + 카테고리 + 내용이 같은 기록 3회 이상 · 5개까지. 패널을 열 때 한 번 계산한다 | 없음 |
| B 채우지 않은 기록 | 공용 기록 중 카테고리가 빈 것, 오늘 포함 7일, 5줄 + 「외 n건」. 줄을 누르면 그 기록의 수정 화면으로 간다(K15) | `sessionStorage` `savely.assistant.unfilledDismissed` — 「나중에 할게요」를 누르면 탭을 닫을 때까지 알리지 않는다 |
| C 고정지출 | 등록 · 보기 · 삭제는 대화로, 고치기는 목록의 줄 → 수정 시트. 등록 · 삭제는 버튼을 눌러야만 일어난다. 「이미 기록했는지」는 공용 기록 기준(구분 + 내용, 내용이 비면 카테고리 이름) | `localStorage` `savely.assistant.recurringAsked`(최초 질문을 한 번 보였는가) · `savely.assistant.recurringSkipped`(「이번 달은 아니에요」 — 항목 번호별 달) |
| E 카드 등록 | 등록만. 등록하면 바로 다음 문장부터 카드 이름을 알아본다 | 없음 |
| F 할 수 있는 일 | 칩은 늘 보인다. 예시를 누르면 입력칸에 채우기만 한다. 날짜 예시는 오늘에서 5일 전 | 없음 |
| G 날짜 읽기 | 규칙 파서가 읽는다. 다른 날에 저장될 카드에만 날짜를 적고, 날짜별로 저장한다 | 없음 |

- **진입 블록은 하나만:** ① 채우지 않은 기록 → ② 나가는 날이 된 고정지출 → ③ 고정지출 최초 질문(방문자당 한 번, K13) → ④ 첫 안내. ②에서 건너뛴 항목은 그 방문자에게만 그 달에 다시 묻지 않는다(K14).
- **앱과 다른 곳:** 「금액이 달라요」는 앱이 시트를 먼저 열고 적용하면 카드를 만드는데, 웹은 카드를 먼저 만들고 바로 수정 시트를 연다(시트를 닫아도 카드는 남는다 — 지울 수 있다). 등록해 둔 금액은 어느 쪽도 바꾸지 않는다.
- 구현: 계산 `src/domain/assistant/AssistantInsights.ts` · `src/domain/recurring/RecurringItem.ts`, 문장 읽는 순서 `src/application/assistant/InterpretSentenceService.ts`, 진입 재료 `GetAssistantEntryService.ts`, 방문자별 표시 `src/lib/assistantPrefs.ts`.

## 4. 기록 종류 · 카테고리 확장 (기록 체험판 영향)

### 4-1. 종류 4가지
| 값 | 화면 표기 | 의미(앱 기준) |
|---|---|---|
| `expense` | 지출 | 가계부 지출 통계에 들어간다 |
| `income` | 수입 | |
| `transfer` | 상환 | 지출 통계에서 뺀다 |
| `savings` | 저축 | |
- 화면에는 한글 표기만 쓴다. 값 이름을 그대로 보여 주지 않는다.
- 결제수단 · 카드 · 이유 · 기분은 **지출에만** 둔다(기존 규칙 유지).

### 4-2. 카테고리 41종 (앱과 id · 이름 · 순서 동일)
- **지출 24:** `food` 식비 · `cafe` 카페 · `grocery` 마트·생필품 · `convenience` 편의점 · `transport` 교통 · `fuel` 주유 · `parking` 주차·통행료 · `car` 차량 정비 · `housing` 주거·관리비 · `telecom` 통신 · `shopping` 쇼핑 · `medical` 병원비 · `beauty` 미용 · `health` 건강·운동 · `culture` 문화·여가 · `subscription` 구독 · `education` 교육 · `travel` 여행 · `alcohol` 술·유흥 · `event` 경조사 · `pet` 반려동물 · `baby` 육아 · `insurance` 보험 · `etc_expense` 기타
- **수입 6:** `salary` 급여 · `allowance` 용돈 · `side_income` 부수입 · `refund` 환급 · `interest` 이자수익 · `etc_income` 기타
- **상환 3:** `card_bill` 카드값 상환 · `loan_payment` 대출 상환 · `interest_payment` 이자 납입
- **저축 8:** `savings_deposit` 예적금 · `emergency_fund` 비상금 · `house_savings` 청약 · `invest` ETF·주식 · `fund` 펀드 · `pension` 연금 · `forex` 외화 · `etc_savings` 기타 저축
- 저축의 「ETF·주식」 · 「펀드」 · 「외화」는 금지 표현에 걸리지 않는다. 앱과 같은 이름으로 쓴다(확정 · U-W7, 2026-11-25).

### 4-3. 화면 반영
- 입력 · 수정 폼: 종류 탭 2개 → 4개. 종류에 맞는 카테고리만 보인다. **카테고리는 선택 사항**이다 — 비워도 저장된다(K7). 수정 화면에서 종류를 바꿀 수 있다(K8). 편의점은 먼저 보여 주는 목록에 넣는다(12개, K8). 카드 이름 칸은 카드 결제일 때만 보인다(K12).
- 목록 · 상세 · 홈 · 달력 · 리포트(0단계 대조 뒤 확정):
  - 금액 · 비율 · 막대 · 카테고리 · 이유 · 기분은 **지출만** 센다. 상환 · 저축 합계를 따로 보여 주는 곳은 만들지 않는다(앱에도 없다).
  - 「기록 n건」(홈 · 달력 · 리포트)은 **4종 모두** 센다(K3).
  - 달력 선택일 패널은 지금 구조(「이 날 쓴 돈」 + 한 목록)를 두고 행에서 구분한다(K4).
  - 리포트 빈 상태와 「지난달 기록 없음」은 **지출 기준**이다 — 수입 · 상환 · 저축만 있는 달은 빈 달이다(K6).
  - 행 제목은 내용 → 카테고리 이름 → 종류 이름 순으로 쓴다. 금액 표기는 K2.
- 카테고리가 비어 있는 지출(B)은 통계에서 **「기타」(`etc_expense`) 한 줄에 합친다**(K5). 리포트 카테고리는 지금처럼 전체를 나열한다(앱의 상위 5 묶음은 따르지 않는다).
- Figma 시안 갱신 필요(폼 · 목록 · 달력 · 리포트).

## 5. 저장 데이터 (D1 `savely-records`)

### 5-1. `records` 바꾸기 — 마이그레이션 `0002`
SQLite는 CHECK를 ALTER로 바꿀 수 없어 테이블을 한 번 다시 만든다(새 테이블 → 복사 → 교체).
| 칸 | 바뀌는 것 |
|---|---|
| `kind` | 4가지 허용 |
| `category_id` | 41종 허용, **비어 있어도 저장**(B) |
| `card_name` | 새 칸. 카드 결제일 때 카드 이름 **20자**(앱 기록 화면 · 초안 검증기와 같다. 서버는 기록에 카드 id만 두고 이름은 보유 카드 표에 50자까지 받는다) |

- 지출이 아니면 결제수단 · 카드 · 이유 · 기분이 비어 있어야 한다(기존 CHECK를 `card_name`까지 넓힘). 카드 이름은 카드 결제일 때만 남긴다(CHECK).
- 파일: `migrations-records/0002_kinds_cards_recurring.sql`(2026-11-25 로컬 적용 · 전후 비교 일치). 마이그레이션과 D1 쿼리는 `src/infrastructure/record/d1.test.ts`가 Node 내장 SQLite로 돌려 본다.

### 5-2. 새 테이블
| 테이블 | 내용 | 한도 |
|---|---|---|
| `cards` | 등록 카드: 이름 · 종류(신용 · 체크) · 만든 시각. 같은 이름은 하나 | 30장 · 이름 20자 |
| `recurring_items` | 고정지출 · 고정수입: 이름 · 금액 · 나가는 날(1~31) · 종류 · 카테고리(선택) · 결제수단 · 카드(선택, 지출만) · 시각. 같은 종류 · 같은 이름은 하나. **건너뛴 달은 여기 두지 않는다** — 방문자별 브라우저 저장소 `localStorage` `savely.assistant.recurringSkipped`(K14) | 30개 · 이름 60자 |

1. 원격 DB 백업: `npx wrangler d1 export savely-records --remote --output=<백업 파일>` (백업 파일은 커밋하지 않는다)

3. 사용자 승인 후 원격 적용

- 사용자가 입력한 문장 · OpenAI 응답 원문 · 대화 내역. 서버 로그에도 남기지 않는다(오류 종류와 시각만).

## 6. OpenAI 계약

### 6-1. 호출
- Responses API(`POST /v1/responses`), 서버(Server Action)에서만.
- 모델: 환경 변수 `OPENAI_MODEL`(기본 `gpt-6-luna`). 모델이 폐기되면 코드 수정 없이 바꾼다.
- 출력: 구조화 출력(JSON 스키마 강제).
- 추론 강도: `low`로 쓴다(2026-11-26 실제 호출로 확인 — 「커피 사천오백」 · 「적금 삼십만 원 넣음」 · 「5달러」(만들지 않음) 등을 맞게 읽었다). `none` 또는 `low` — 품질 · 비용을 재고 정한다. `gpt-6-luna`가 받는 값은 `none` · `low` · `medium` · `high` · `xhigh` · `max`이고 `minimal`은 없다).
- 출력 토큰 상한 · 시간 초과 10초.
- 응답 보관 설정: `store: false`를 넣는다(기본값은 30일 보관). 그래도 남용 모니터링 로그는 최대 30일 남을 수 있다(OpenAI 문서, 2026-11-25 확인) — 처리방침에 그대로 적는다(K19).
- 구조화 출력은 `text.format`에 `type: "json_schema"` · `strict: true`를 넣는다(기본값 false). 결과는 `output[]`의 `message` → `content[]`의 `output_text`에서 꺼낸다(SDK 없이 부르면 최상위 `output_text`가 없다). `status: "incomplete"` · `refusal`은 읽지 못한 것으로 본다.
- 카드 이름 출력은 스키마에서 「등록된 카드 이름 중 하나 또는 빈 값」으로 제한한다(K21).

### 6-2. 보내는 것
- 오늘 날짜 · 화면 날짜(Asia/Seoul), 종류 · 카테고리 목록(id · 이름), 결제수단 목록, 등록된 카드 이름 목록
- 규칙이 읽지 못한 조각(합계 500자 이내)
- **보내지 않는 것:** 규칙이 읽은 부분 · 다른 기록 · 이전 대화 · IP 등 식별 정보

### 6-3. 받는 것 (JSON)
```json
{
  "drafts": [
    { "piece": 0, "kind": "expense", "amount": 12000, "date": null,
      "category_id": "grocery", "title": "다이소 수납함", "payment_method": null, "card_name": null }
  ],
  "unreadable": [1]
}
```
- `drafts` 항목에 **이유 · 기분 · 메모 칸이 없다**(원칙 2).
- **OpenAI가 쓴 자유 문장은 화면에 보여 주지 않는다.** 안내 문장은 모두 앱 문구다 — 문구 규칙 위반 · 프롬프트 인젝션 문장이 화면에 나갈 길이 없다.

### 6-4. 검증 (OpenAI 출력은 믿지 않는다)
- 형식 · 타입 검사. 실패하면 그 조각은 읽지 못한 것으로 본다.
- 각 초안은 규칙 초안과 같은 검증기로: 금액 범위, 날짜(오늘~30일 전), 종류-카테고리 일치, 내용 60자, 카드 이름은 등록된 카드와 같을 때만 채운다.
- 저장은 기존 저장 경로로만 한다(검증 · 저장소 동일).

### 6-5. 키 · 설정
| 이름 | 위치 | 상태 |
|---|---|---|
| `OPENAI_API_KEY` | 운영: Cloudflare 비밀 값(`wrangler secret put`) · 로컬: `.dev.vars` | 2026-11-25 등록(사용자) |
| `OPENAI_MODEL` | `wrangler.jsonc` `vars` | 2026-11-26 추가(`gpt-6-luna`) |
- Wrangler 설정에 `"secrets": { "required": ["OPENAI_API_KEY"] }`를 둬 키가 빠진 채 배포되지 않게 한다. 이 설정을 쓰면 목록에 없는 `.dev.vars` 값은 로컬에서 읽히지 않는다 — 지금 `.dev.vars`에는 이 키 하나뿐이다(사용자 확인, K20).
- 잔액 소진은 HTTP 429 · `error.code: "credit_balance_exhausted"`(`error.type`이 `insufficient_quota`일 수 있다)로 온다. 재시도하지 않는다.
- `.dev.vars.example`에는 이름만 적는다. 값은 코드 · 문서 · GitHub 어디에도 두지 않는다.

## 7. 비용 · 남용 방지

| 장치 | 값 |
|---|---|
| 결제 | 선불 $5 · 자동 충전 꺼짐 · 프로젝트 지출 한도 $5(추가 지출 막음, 사용자 설정 2026-11-25) → **최대 비용 $5.** 잔액이 떨어지면 OpenAI만 멈추고 규칙 파서는 계속 동작. 소진 직후 잠깐 더 처리될 수 있다는 것이 OpenAI 문서에 있어 지출 한도를 함께 건다(K18) |
| OpenAI 프로젝트 | `savely-web` 전용 키 · 권한은 Responses 쓰기만. 모델은 `gpt-6-luna`만 허용(사용자 설정 2026-11-25, K18). 요청에 `service_tier: "default"`를 직접 넣어 빠른 처리 등급(2배 가격)을 쓰지 않는다 |
| OpenAI 호출 요청 제한 | 새 바인딩 `ASSISTANT_RATE_LIMITER` — 같은 IP 1분 6회 (제안) |
| 하루 전체 상한 | OpenAI 호출 300회(Asia/Seoul 날짜, 제안). 넘으면 그날은 규칙만 |
| 입력 | 500자 · 초안 20건 |
| 문장 보내기 요청 제한 | 새 바인딩 — 같은 IP 1분 20회 (제안, K17). 넘으면 기존 E12 문구 |
| 고정지출 · 카드 등록 · 삭제 | 기존 기록 쓰기 제한(1분 10회)을 함께 쓴다 (K17) |
| 여러 건 저장 | 저장 확인 한 번 = 요청 1회로 센다. 지금 기록 쓰기 제한(1분 10회)에 20건이 걸리지 않게 (제안). 초안 카드마다 브라우저가 UUID를 만들고 서버는 형식을 검사한 뒤 같은 id가 이미 있으면 넣지 않는다 — 다시 눌러도 중복되지 않는다(K16) |
| 시간 초과 | 10초 |
- 비용 가정(측정 전): 1회 입력 3,000 · 출력 1,500 토큰이면 약 $0.001. 하루 상한 300회를 매일 채워도 하루 약 $0.32다. 실제 값은 개발 중 토큰 수로 재서 README에 적는다(문장은 기록하지 않는다).
- **측정(2026-11-26, 로컬 · 실제 키 · 호출 11회):** 1회 입력 약 1,260 ~ 1,290 · 출력 23 ~ 220 토큰(추론 포함). 가격표(입력 $0.1 · 출력 $0.5 / 100만)로 1회 약 $0.00014 ~ $0.00024, 하루 상한 300회를 모두 써도 하루 약 $0.07이다. 응답까지 1.6 ~ 4.7초. 서버 로그에는 토큰 수(숫자 두 개)와 실패 종류만 남는다.
- **구현(2026-11-26):** 바인딩 `ASSISTANT_RATE_LIMITER`(OpenAI 호출, 같은 IP 1분 6회) · `ASSISTANT_SEND_RATE_LIMITER`(문장 보내기, 같은 IP 1분 20회 — 넘으면 「요청이 너무 많아요. 잠시 후 다시 시도해 주세요」). 하루 상한 300회는 `assistant_usage`에서 「상한보다 작을 때만 +1」 한 문장으로 센다. 어느 한도에 걸려도 규칙 파서 결과는 그대로 나온다.

## 8. 개인정보 · 보안

- **전송 고지:** 입력칸 아래 상시 표시(문구 §10 W2, 확정 · U-W6).

## 11. QA (요약)
