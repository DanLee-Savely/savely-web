## 1. 목적과 범위

### 1-1. 검증할 가치
세이블리의 출발점인 「직접 적는다」를 웹에서 검증한다.
방문자가 지출 · 수입 한 건을 적고(등록), 쌓인 기록을 훑고(목록), 한 건을 자세히 보고(상세), 고치고(수정), 지운다(삭제).

### 1-2. 이번에 만드는 것
- 등록 → 목록 → 상세 → 수정 → 삭제 한 사이클 (Cloudflare D1에 저장)
- 기록 한 건당 사진 1장 (Cloudflare R2)
- 홈 · 달력 · 리포트 — 기록을 모아 읽기만 하는 화면(쓰기 없음). A안, 사용자 2026-11-10 (§4-8 ~ §4-10)
- 목록 페이지 나누기 · 입력 검증과 오류 문구 · 두 번 저장 방지 · 로딩 / 오류 / 빈 상태 · 없는 주소 안내
- 문서: 이 명세 · 테이블 구조 · QA 체크리스트(§10) · README 갱신

### 1-3. 이번에 만들지 않는 것

| 기능 | 빼는 이유 |
|---|---|
| 로그인 · 회원가입 · 사용자별 권한 | 미션 공지가 미션 7로 넘김 |
| 정산 · 연속 정산 · 완벽한 주 · 보상(SVX) | 한 사람의 기록이 전제인 기능이라 로그인 없이는 숫자의 주인이 없음. 문구 규칙상 SVX는 로그인 후 화면 전용. 대시보드 시안(2026-11-04)의 정산 · 연속 · 적립 카드도 같은 이유로 뺀다 |
| AI 리포트 · 멤버십 | 로그인 · 유료 기능 전제. 범위 밖 (홈 · 달력 · 리포트는 2026-11-10 A안으로 범위에 넣음) |
| 상환 · 저축 유형, 카드 이름 | 앱에는 있으나 MVP 검증에 필요 없음. 카드 이름은 개인정보에 가까움 |

### 1-4. 공개 체험 전제 (중요)
- 로그인이 없으므로 **모든 방문자가 같은 데이터를 함께 보고, 고치고, 지울 수 있다.**
- 그래서 /app 모든 화면 위에 「실제 소비 내역 · 개인정보를 적지 말라」는 안내 띠(문구 N1)를 둔다.
- 저장되는 데이터는 체험용 예시로 취급한다. 앱 서버(savely-backend)의 실제 기록과 연결되지 않는다.

## 2. 사용자 흐름

```
목록 /app/records ──(행 선택)──▶ 상세 /app/records/[id] ──(수정)──▶ 수정 /app/records/[id]/edit
   │                                 ▲   │                                   │
   │                                 │   └──(삭제 → 확인)──▶ 목록 + 「기록을 삭제했어요」
   │                                 └────────────(저장 성공 + 「수정했어요」)──┘
   │
   └──(기록하기)──▶ 등록 /app/records/new ──(저장 성공)──▶ 상세 + 「기록했어요」
```

- 저장 성공 후 상세로 보내는 이유: 방금 적은 내용과 사진이 제대로 저장됐는지 곧바로 확인시키기 위해서다.
- 어느 화면에서든 왼쪽 메뉴(홈 · 기록 · 달력 · 리포트)로 이동할 수 있다. 상세에서는 「목록으로」.
- 홈(`/app`)의 카드에서 기록 목록 · 달력 · 리포트로 이동하고, 달력의 「이 날 기록 추가」는 그 날짜로 등록 화면을 연다.

## 3. 라우트

| 주소 | 화면 | 파일 (App Router) | 비고 |
|---|---|---|---|
| `/app` | 홈 | `src/app/app/page.tsx` | 기록을 모아 보여 줌 (M2, §4-8) |
| `/app/records?page=N` | 목록 | `src/app/app/records/page.tsx` | N 기본값 1 |
| `/app/calendar?month=YYYY-MM&date=YYYY-MM-DD` | 달력 | `src/app/app/calendar/page.tsx` | §4-9 |
| `/app/report?month=YYYY-MM` | 리포트 | `src/app/app/report/page.tsx` | §4-10 |
| `/app/records/new?date=YYYY-MM-DD` | 등록(날짜 채움) | 등록과 같음 | 달력에서 진입 (§4-9) |
| `/app/records/new` | 등록 | `src/app/app/records/new/page.tsx` | |
| `/app/records/[id]` | 상세 | `src/app/app/records/[id]/page.tsx` | 동적 라우트 |
| `/app/records/[id]/edit` | 수정 | `src/app/app/records/[id]/edit/page.tsx` | |
| — | 없는 기록 안내 | `src/app/app/records/[id]/not-found.tsx` | `notFound()` 호출 시 |
| — | 로딩 · 오류 | 목록 · 상세 폴더마다 `loading.tsx` · `error.tsx` | |
| `/app/records/[id]/image` | 사진 전달 | `src/app/app/records/[id]/image/route.ts` | R2에서 꺼내 전달(§6-4) |

- **쓰기**(등록 · 수정 · 삭제)는 Server Actions로 처리한다: `src/app/app/records/actions.ts`.
  Action은 FormData를 읽어 서비스(§7)에 넘기고, 도메인 오류를 칸별 문구로 바꾸는 일만 한다.
- **읽기**(목록 · 상세)는 서버 컴포넌트에서 서비스를 호출한다.
- `[id]`가 UUID 형식이 아니면 DB를 조회하지 않고 바로 없는 기록 안내를 보여 준다.

## 4. 화면별 명세

### 4-1. 목록 `/app/records`

| 구분 | 내용 |
|---|---|
| 표시 | 위: 제목 「기록」, 총 건수(「전체 128건」), 「기록하기」 버튼 · 본문: 기록 행 · 아래: 페이지 나누기 |
| 기록 행 | 카테고리 아이콘 · 내용(비었으면 카테고리 이름) · 보조줄(카테고리 · 결제수단 · 왜 썼나요, 수입은 카테고리만) · 날짜(「10월 26일 (월)」) · 금액(지출 「9,000원」, 수입 「+3,000,000원」 초록) · 사진이 있으면 사진 아이콘 |
| 정렬 | 날짜 최신순, 같은 날짜는 만든 시각 최신순 |
| 페이지 | 한 페이지 10건 (제안 M5). 「이전」 · 「다음」 + 번호(현재 페이지 중심 최대 5개). 1페이지의 「이전」, 마지막 페이지의 「다음」은 비활성 |
| 행동 | 행 클릭 → 상세 · 「기록하기」 → 등록 · 번호 클릭 → `?page=N` |
| 성공 결과 | 기록이 정렬 순서대로 보이고, 주소의 page와 화면의 현재 페이지가 같다 |
| 빈 상태 | 기록 0건: 「아직 기록이 없어요」 + 「첫 기록 남기기」(→ 등록) |
| 로딩 | 기록 행 모양의 회색 막대 10줄 |
| 오류 | 「기록을 불러오지 못했어요」 + 「다시 시도」 |
| 잘못된 page | 숫자가 아니거나 1보다 작으면 1페이지를 보여 준다. 마지막 페이지보다 크면 마지막 페이지로 이동한다 |

### 4-2. 상세 `/app/records/[id]`

| 구분 | 내용 |
|---|---|
| 표시 | 구분(지출 / 수입) · 금액(큰 글씨) · 날짜(요일 포함) · 카테고리 · 결제수단 · 왜 썼나요 · 그때 기분 · 내용 · 메모 · 사진 · 「처음 적은 시각 · 마지막으로 고친 시각」 |
| 빈 선택 항목 | 줄을 숨기지 않고 「—」로 표시한다(수정으로 채울 수 있음을 보여 줌) |
| 사진 | 있으면 가로 최대 640px로 표시하고, 누르면 원본 크기로 새 탭에서 연다. 없으면 「첨부한 사진이 없어요」 자리 표시. 불러오기 실패 시 「사진을 불러오지 못했어요」 |
| 행동 | 「수정」 → 수정 화면 · 「삭제」 → 확인 창(4-5) · 「목록으로」 → `/app/records` |
| 알림 | 등록 · 수정 직후 들어오면 「기록했어요」 / 「수정했어요」 알림(3초) |
| 실패 | 없는 id · 형식이 틀린 id → 없는 기록 안내(4-6) · 조회 오류 → 오류 화면 |

### 4-3. 등록 `/app/records/new`

**입력 항목** — 항목 · 값은 앱과 서버에 맞추고, 글자 수는 앱 화면 기준이다.

| 항목 | 필수 | 규칙 | 기본값 | 오류 문구 |
|---|---|---|---|---|
| 구분 | 필수 | 지출 · 수입 중 하나 | 지출 | — (항상 값이 있음) |
| 금액 | 필수 | 숫자만 · 1원 이상 1조 원 미만(앱 서버와 같음, M6) · 입력 중 쉼표 자동 | 빈칸 | 비었을 때 E1 · 범위 밖 E2 |
| 날짜 | 필수 | 오늘(한국 시간)까지 · 미래 불가(앱과 같음) | 오늘 | 비었을 때 E13 · 미래 E3 |
| 카테고리 | 필수 | 구분별 목록(§6-3) 중 하나 | 없음 | E4 |
| 내용 | 선택 | 60자 이내(앱 「내용」과 같음) | 빈칸 | E5 |
| 결제수단 | 선택 · 지출만 | §6-3 목록 | 없음 | — |
| 왜 썼나요 | 선택 · 지출만 | §6-3 목록 | 없음 | — |
| 그때 기분 | 선택 · 지출만 | §6-3 목록 | 없음 | — |
| 메모 | 선택 | 200자 이내(앱과 같음) | 빈칸 | E6 |
| 사진 | 선택 | 1장 · JPG / PNG / WEBP · 5MB 이하 (제안 M4) | 없음 | 형식 E7 · 크기 E8 |

- 화면 배치(PC): 왼쪽 열(구분 · 금액 · 날짜 · 내용 · 메모), 오른쪽 열(카테고리 · 지출 정보), 맨 오른쪽 카드(사진). Figma 「MVP · 등록」 참고.
- 카테고리는 먼저 보여 줄 11개(제안 — 사용 빈도 근거 없음, 일상 지출 위주로 고름: 식비 · 카페 · 마트·생필품 · 교통 · 주유 · 쇼핑 · 통신 · 구독 · 문화·여가 · 병원비 · 미용)와 「더보기 +12」를 먼저 보여 주고, 「더보기」를 누르면 나머지를 펼친다. 수입은 6개 모두 보여 준다.
- 구분을 「수입」으로 바꾸면 결제수단 · 왜 썼나요 · 그때 기분 칸을 숨기고 값도 비운다. 카테고리는 수입 목록으로 바뀌고 선택이 풀린다.
- 사진을 고르면 미리보기와 「삭제」 버튼을 보여 준다. 올리기 전에 브라우저에서 긴 변 1600px 이하로 줄여 다시 저장한다(사진 속 위치 정보 제거 — §8-3).

**행동과 결과**

| 행동 | 결과 |
|---|---|
| 「저장하기」 | ① 브라우저 검증 → 실패하면 해당 칸 아래 오류 문구, 첫 오류 칸으로 스크롤 · 포커스 ② 버튼이 「저장 중…」으로 바뀌고 비활성, 입력 칸과 사진 버튼도 잠금(두 번 저장 방지) ③ 서버 검증(같은 규칙) → 사진 업로드 → 기록 저장 ④ 성공: 상세로 이동 + 「기록했어요」 |
| 서버 검증 실패 | 같은 오류 문구를 칸 아래 표시, 입력값 유지 |
| 사진 업로드 실패 | 기록을 저장하지 않는다. 폼 위에 E9, 입력값 유지(사진을 다시 고르거나 빼고 저장 가능) |
| 저장 실패(네트워크 · DB) | 폼 위에 E10, 입력값 유지. 이미 올라간 사진은 지운다 |
| 「취소」 | 목록으로 이동(확인 창 없음) |

### 4-4. 수정 `/app/records/[id]/edit`
- 등록과 같은 폼에 기존 값을 채워 연다. 제목 「기록 수정」, 버튼 「수정하기」.
- 위쪽 돌아가기 링크는 「상세로」, 「취소」도 상세로 돌아간다(등록의 「취소」는 목록).
- 사진: 기존 사진 미리보기 + 「바꾸기」 · 「삭제」. 바꾸거나 지웠다면 저장 성공 후 이전 사진을 R2에서 지운다.
- 성공: `updated_at` 갱신 → 상세로 이동 + 「수정했어요」.
- 실패: 등록과 같다. 수정 화면을 연 뒤 다른 방문자가 그 기록을 지웠다면 저장 시 없는 기록 안내(4-6)로 보낸다.
- 없는 id로 들어오면 없는 기록 안내.

### 4-5. 삭제 (상세 화면의 확인 창)

| 구분 | 내용 |
|---|---|
| 창 | 제목 「이 기록을 삭제할까요?」 · 본문 「삭제하면 되돌릴 수 없어요. 첨부한 사진도 함께 지워져요.」 · 지울 기록 요약(아이콘 · 내용 · 날짜 · 금액) · 버튼 「취소」 · 「삭제」(위험 색) |
| 행동 | 「삭제」 → 「삭제 중…」 비활성 → 기록 삭제 → 사진 삭제 → 목록으로 + 「기록을 삭제했어요」 |
| 실패 | 창 안에 E11, 창 유지 |
| 이미 지워진 기록 | 목록으로 + 「이미 삭제된 기록이에요」 |
| 닫기 | 「취소」 · Esc · 창 바깥 클릭 |

- 삭제는 행을 실제로 지운다(제안 M7). 앱 서버는 `deleted_at` 소프트 삭제를 쓰지만 MVP는 단순하게 간다.

### 4-6. 없는 기록 안내 (not-found)
- 「찾는 기록이 없어요」 · 「삭제됐거나 주소가 잘못됐어요」 + 「목록으로」 버튼. HTTP 상태 404.

### 4-7. 공통
- /app 모든 화면 위에 안내 띠(N1).
- 왼쪽 메뉴: 홈 · 기록 · 달력 · 리포트(M3). 정산 · 보상 · 멤버십 · 마이페이지는 로그인 이후.
- 알림(토스트)은 화면 아래 가운데에 3초.

### 4-8. 홈 `/app` (A안 — 사용자 2026-11-10)
기록 테이블만 읽어 계산하는 화면이다. 쓰기 · 정산 · 보상은 없다. 「오늘」은 항상 Asia/Seoul 날짜다.

| 구분 | 내용 |
|---|---|
| 상단 | 작은 글씨: 오늘 날짜(「10월 26일 (월)」). 제목: 오늘 기록 건수에 따라 바뀜(앱 홈과 같은 문구) — 0건 「오늘은 아직 적지 않았어요.」, 1건 이상 「오늘 {n번} 적었어요.」(1~5건은 한 · 두 · 세 · 네 · 다섯 번, 6건부터 「6번」). 오른쪽 「+ 기록하기」(→ 등록) |
| 오늘 카드 | 「기록 {n}건」(지출 + 수입) · 오늘 쓴 돈(지출 합계) · 오늘 기록 최근 만든 순 최대 3건(행 클릭 → 상세) · 「기록 전체」(→ 목록). 0건이면 「한 건만 적어도 오늘이 시작됩니다」(앱 문구) + 「첫 기록 남기기」 |
| 이번 달 카드 | 제목 「{M}월 1일 – {오늘}일」 · 이번 달 쓴 돈(지출 합계) · 수입(+금액, 초록) · 기록 건수 · 하루 평균 지출 · 「리포트」(→ 리포트) |
| 최근 7일 카드 | 오늘 포함 7일의 날짜별 지출 막대 + 7일 합계. 오늘 막대만 진한 색. 지출 0인 날은 높이 최소 막대와 「0」. 「달력」(→ 달력) |
| 많이 쓴 곳 카드 | 이번 달 지출 카테고리 상위 3개: 아이콘 · 이름 · 비율(%) · 금액 · 막대(1위 대비 길이). 이번 달 지출 0건이면 「기록이 쌓이면 많이 쓴 곳을 보여 드려요」 |
| 로딩 · 오류 | 카드 모양 스켈레톤 / 목록과 같은 오류 화면(X2) |

**계산 규칙**
- 이번 달 = 1일 ~ 오늘. 하루 평균 지출 = 이번 달 지출 합계 ÷ 오늘 날짜(경과 일수), 원 단위 반올림.
- 비율(%) = 카테고리 지출 합계 ÷ 이번 달 지출 합계 × 100, 정수 반올림.
- 수입은 「수입」 줄에만 쓰고 쓴 돈 · 비율 · 막대에는 넣지 않는다.

### 4-9. 달력 `/app/calendar?month=YYYY-MM&date=YYYY-MM-DD`

| 구분 | 내용 |
|---|---|
| 상단 | 제목 「달력」 · 오른쪽 달 이동(‹ 2026년 10월 ›). 다음 달은 이번 달이면 비활성(미래 달 없음) |
| 달력 카드 | 위: 「{M}월 지출 {합계}원」 · 「기록 {n}건」. 월요일 시작 7칸 × 주 수(앱과 같은 월 ~ 일). 칸: 날짜 + 그날 지출 합계(0이면 비움). 앞뒤 다른 달 날짜는 흐리게, 누를 수 없음. 오늘은 초록 테두리 + 「오늘」. 선택한 날은 연한 초록 배경. 미래 날짜는 금액 없음 · 선택 불가 |
| 범례 | 오늘 · 선택한 날 · 「하루 평균 {금액}원」(이번 달은 경과 일수, 지난 달은 그 달 일수로 나눔) |
| 선택한 날 패널 | 날짜(요일) · 이 날 쓴 돈(지출 합계) · 「기록 {n}건」 · 「필수지출 {n}건」(1건 이상일 때만) · 기록 목록(최근 만든 순, 행 클릭 → 상세) · 그때 기분 집계(1건 이상인 기분만 칩으로) · 「이 날 기록 추가」(→ `/app/records/new?date=YYYY-MM-DD`). 기록 없는 날은 「이 날은 기록이 없어요」 + 같은 버튼 |
| 기본 선택 | `date`가 없거나 그 달 밖이거나 미래면: 이번 달은 오늘, 지난 달은 그 달 마지막 날 |
| 잘못된 month | 형식이 틀리거나 미래 달이면 이번 달로 보여 준다 |
| 빈 달 | 칸은 모두 비고, 패널은 「이 날은 기록이 없어요」 |

- 등록 화면은 `?date=`가 올바른 과거 · 오늘 날짜면 그 날짜로 채워 연다(아니면 오늘).

|---|---|---|---|

### 6-1. 테이블 `records`
열 이름과 값은 앱 서버(`savely-backend`의 `model Record`)와 맞춘다. 나중에 실제 서버로 옮길 때 변환을 줄이기 위해서다.

| 열 | 타입 (SQLite) | 필수 | 규칙 | 설명 |
|---|---|---|---|---|
| `id` | TEXT | O | PK · UUID(v4)를 서버 코드가 만든다(사진 키에 쓰기 위해 저장 전에 만듦) | 기록 고유 번호 |
| `kind` | TEXT | O | `expense` · `income`, 기본 `expense` | 구분 |
| `amount` | INTEGER | O | 1 ~ 999,999,999,999 | 금액(원, 정수) |
| `record_date` | TEXT | O | `'YYYY-MM-DD'`(한국 날짜). 미래 불가는 서버 코드에서 검사 | 기록 날짜. 앱 서버와 같은 문자열 방식 |
| `category_id` | TEXT | O | §6-3 목록 · 구분과 맞아야 함 | 카테고리 |
| `title` | TEXT | — | 60자 이내 | 내용 |
| `payment_method` | TEXT | — | §6-3 · 지출만 | 결제수단 |
| `reason` | TEXT | — | §6-3 · 지출만 | 왜 썼나요 |
| `feeling` | TEXT | — | §6-3 · 지출만 | 그때 기분 |
| `memo` | TEXT | — | 200자 이내 | 메모 |
| `image_key` | TEXT | — | R2 객체 키 | 사진 |
| `created_at` | TEXT | O | ISO 8601 UTC 문자열, 서버 코드가 넣는다 | 만든 시각 |
| `updated_at` | TEXT | O | 수정할 때마다 서버 코드가 갱신 | 고친 시각 |

- SQLite에는 uuid 타입과 시간대가 붙은 시각 타입이 없어 문자열로 저장한다. 고유 번호와 시각은 DB 기본값이 아니라 서버 코드가 만든다. 시각은 `Clock` 인터페이스로 받아 테스트에서 고정할 수 있게 한다.
- **「미래 불가」를 DB 제약으로 걸지 않는 이유:** DB의 「오늘」은 UTC 기준이라 한국 시간 0~9시에는 하루가 어긋난다. 서버 코드에서 Asia/Seoul 기준으로 검사한다.
- **카테고리는 별도 테이블 없이 코드 상수로 둔다(제안).** 값 검사는 DB CHECK 제약과 서버 코드 양쪽에서 한다.

### 6-2. 테이블 생성 SQL (D1 마이그레이션 `migrations-records/0001_create_records.sql`)

```sql
CREATE TABLE records (
  id             TEXT PRIMARY KEY,
  kind           TEXT NOT NULL DEFAULT 'expense'
                 CHECK (kind IN ('expense', 'income')),
  amount         INTEGER NOT NULL
                 CHECK (amount BETWEEN 1 AND 999999999999),
  record_date    TEXT NOT NULL
                 CHECK (record_date GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]'),
  category_id    TEXT NOT NULL CHECK (category_id IN (
                   'food','cafe','grocery','transport','fuel','parking','car','housing',
                   'telecom','shopping','medical','beauty','health','culture','subscription',
                   'education','travel','alcohol','event','pet','baby','insurance','etc_expense',
                   'salary','allowance','side_income','refund','interest','etc_income')),
  title          TEXT CHECK (title IS NULL OR length(title) <= 60),
  payment_method TEXT CHECK (payment_method IN
                   ('cash','check_card','credit_card','bank_transfer','other')),
  reason         TEXT CHECK (reason IN ('need','impulse','value','fixed','other')),
  feeling        TEXT CHECK (feeling IN ('proud','satisfied','meh','unsatisfied','regret')),
  memo           TEXT CHECK (memo IS NULL OR length(memo) <= 200),
  image_key      TEXT,
  created_at     TEXT NOT NULL,
  updated_at     TEXT NOT NULL,
  -- 수입에는 지출 전용 항목을 넣지 않는다
  CHECK (kind = 'expense' OR (payment_method IS NULL AND reason IS NULL AND feeling IS NULL))
);

-- 목록 정렬 · 페이지 나누기용
CREATE INDEX records_date_idx ON records (record_date DESC, created_at DESC);
```

- 출시 알림 마이그레이션(`migrations/`)과 섞이지 않게 폴더를 나눈다. wrangler 설정의 `d1_databases` 항목에서 데이터베이스별로 마이그레이션 폴더를 지정한다(정확한 설정 이름은 적용할 때 wrangler 공식 문서로 확인).
- 구분과 카테고리가 맞는지(지출에 「급여」가 들어가지 않는지)는 DB가 아니라 서버 코드(`RecordEntry`)에서 검사한다.
- **페이지 나누기:** `ORDER BY record_date DESC, created_at DESC LIMIT 10 OFFSET ?`와 `SELECT COUNT(*) FROM records`.
- **수정:** `UPDATE ... SET ..., updated_at = ? WHERE id = ?`. 바뀐 행이 0개면 그사이 삭제된 것이므로 `RecordNotFoundError`.
- 값은 모두 바인딩 파라미터(`?`)로 넘긴다. SQL 문자열에 입력값을 이어 붙이지 않는다.

### 6-3. 값 목록 (DB 값 ↔ 화면 표시)
모두 앱 `record.dart` · `seed.dart`, 서버 `schema.prisma`와 같은 값이다. 화면에는 영문 값을 절대 노출하지 않는다(앱 규칙과 같음).

**구분 `kind`:** `expense` 지출 · `income` 수입

**결제수단 `payment_method`:** `cash` 현금 · `check_card` 체크카드 · `credit_card` 신용카드 · `bank_transfer` 계좌이체 · `other` 기타

**왜 썼나요 `reason`:** `need` 필요해서 · `impulse` 충동적 · `value` 가치소비 · `fixed` 필수지출 · `other` 기타

**그때 기분 `feeling`:** `proud` 뿌듯 · `satisfied` 만족 · `meh` 그냥 · `unsatisfied` 아쉬움 · `regret` 후회

**지출 카테고리 (23개):**
`food` 식비 · `cafe` 카페 · `grocery` 마트·생필품 · `transport` 교통 · `fuel` 주유 · `parking` 주차·통행료 · `car` 차량 정비 · `housing` 주거·관리비 · `telecom` 통신 · `shopping` 쇼핑 · `medical` 병원비 · `beauty` 미용 · `health` 건강·운동 · `culture` 문화·여가 · `subscription` 구독 · `education` 교육 · `travel` 여행 · `alcohol` 술·유흥 · `event` 경조사 · `pet` 반려동물 · `baby` 육아 · `insurance` 보험 · `etc_expense` 기타

**수입 카테고리 (6개):**
`salary` 급여 · `allowance` 용돈 · `side_income` 부수입 · `refund` 환급 · `interest` 이자수익 · `etc_income` 기타
- 「이자수익」은 문구 규칙의 금지 표현 「수익」을 포함하지만 앱 · 서버와 같은 이름이라 예외로 둔다(사용자 2026-11-10).

### 6-4. R2 (사진)

| 항목 | 내용 |
|---|---|
| 버킷 | `savely-record-images` (제안). **공개 주소를 만들지 않는다** |
| 읽기 | 서버 경로 `GET /app/records/[id]/image`(Route Handler)가 R2에서 꺼내 전달한다. 기록이나 사진이 없으면 404 |
| 쓰기 | 서버(Server Action)만. 브라우저는 R2에 직접 접근하지 않는다 |
| 허용 형식 · 크기 | JPG · PNG · WEBP, 5MB 이하. 서버 코드에서 확장자가 아니라 파일 앞부분 바이트(시그니처)로 실제 형식을 확인하고 크기를 검사한다 |
| 키 | `{record_id}/{무작위 uuid}.{jpg\|png\|webp}`. 원래 파일 이름은 저장하지 않는다(이름에 개인정보가 들어갈 수 있음) |
| 정리 | 기록 삭제 · 사진 교체 · 사진 삭제 시 이전 객체를 지운다. 객체 삭제만 실패하면 기록 처리는 성공으로 두고 서버 로그에 기록 id를 남긴다 |
| 전송 크기 | Next.js Server Actions의 요청 본문 기본 한도는 1MB다(Next.js 문서). 브라우저에서 긴 변 1600px로 줄여도 1MB를 넘을 수 있으므로 설정에서 한도를 6MB로 올린다. Next 16의 정확한 설정 이름은 적용할 때 공식 문서로 확인한다 |

### 6-5. 집계 조회 (홈 · 달력 · 리포트, 읽기 전용)
새 테이블 없이 `records`만 읽는다. 기간 조건은 모두 `record_date BETWEEN ? AND ?`(문자열 비교, 기존 인덱스 사용).

| 용도 | 조회 |
|---|---|
| 구분별 합계 · 건수 | `SELECT kind, SUM(amount), COUNT(*) … GROUP BY kind` |
| 날짜별 지출 | `SELECT record_date, SUM(amount) … WHERE kind='expense' … GROUP BY record_date` |
| 카테고리별 지출 | `SELECT category_id, SUM(amount) … WHERE kind='expense' … GROUP BY category_id ORDER BY 2 DESC` |
| 이유 · 기분 건수 | `SELECT reason, COUNT(*) …` · `SELECT feeling, COUNT(*) …`(지출, NULL 제외) |

| 하루 기록 | `SELECT * … WHERE record_date = ? ORDER BY created_at DESC` |

## 8. 데이터 처리 규칙

### 8-1. 접근
- D1 · R2는 Cloudflare **바인딩**(`RECORDS_DB` · `RECORD_IMAGES`)으로 서버 코드에서만 접근한다. 바인딩은 브라우저 코드에 존재하지 않으므로 브라우저에서 데이터베이스나 버킷에 직접 닿을 수 없다. 별도의 데이터베이스 비밀 키는 없다.
- 바인딩은 `wrangler.jsonc`에 선언하고, 코드에서는 `container.ts`의 `getCloudflareContext()`로만 꺼낸다(출시 알림과 같은 방식).
- README에는 바인딩 이름만 적는다. Cloudflare 계정 정보 · API 토큰은 문서와 GitHub에 올리지 않는다. 로컬 비밀 값 파일(`.env*` · `.dev.vars*`)이 `.gitignore`로 제외돼 있음을 확인했다(2026-11-09).
- 로컬 개발은 출시 알림과 같은 개발 환경(OpenNext 개발 모드의 로컬 D1 · R2)을 쓴다. 실서비스 데이터에 붙지 않는다.
- 쓰기(등록 · 수정 · 삭제)는 요청 제한(M15)을 통과해야 한다. 넘으면 E12.

### 8-2. 검증
- 브라우저와 서버가 **같은 도메인 클래스**로 검증한다.
- 브라우저 검증은 우회할 수 있으므로 서버 검증을 생략하지 않는다.
- DB CHECK 제약은 마지막 방어선이다. 정상 흐름에서는 서버 코드가 먼저 거른다.

### 8-3. 개인정보
- 실제 개인정보나 민감한 데이터를 저장하지 않는다(미션 공지). 카드 이름 칸을 두지 않는다.
- 휴대폰 사진에는 찍은 위치(GPS) 같은 정보(EXIF)가 들어 있을 수 있고, 로그인이 없어 누구나 사진을 열어 볼 수 있다. 그래서 올리기 전에 브라우저에서 사진을 다시 저장해 이 정보를 지운다.
- 원래 파일 이름은 저장하지 않는다.
- 로그에는 금액 · 내용 · 메모를 남기지 않는다. 기록 id와 오류 종류만 남긴다.

### 8-4. 날짜와 시간
- 「오늘」은 항상 Asia/Seoul 기준으로 계산한다. 서버(UTC)의 로컬 시간을 쓰지 않는다.
- 날짜는 `'YYYY-MM-DD'` 문자열 그대로 다룬다(앱 서버 `record_date`와 같은 원칙).
- `new Date('YYYY-MM-DD')`로 바꾸지 않는다. 날짜만 있는 문자열은 UTC로 해석돼 하루 밀릴 수 있다.

| Q28 | 주 구간 | 28일 · 30일 · 31일인 달 리포트 | 구간 4개 / 5개(29–30일) / 5개(29–31일) |

| Q30 | 오늘 기준 | 한국 시간 0~9시에 홈 · 달력 열기 | 「오늘」이 한국 날짜 |
